# bookgen — generate a Learn-by-LLM book around a real codebase

You are scaffolding a multi-session learning book around a real cumulative project the learner builds (or tours) chapter by chapter, in a target language they want to learn. The agent acts as a *thinking companion* rather than a *solution provider*.

## Why bookgen exists — the category move

The same coding agent, in a different stance, can also teach. Bookgen creates the project-specific material that lets it do so.

A bookgen-scaffolded repo is the artifact that makes this category move concrete for one specific codebase + language combination. The learner forks the repo, opens it in an LLM-aware coding agent, and the agent already knows it's a teacher (because the vendored skill says so) for this specific topic (because the chapters say so).

The era's specific failure mode this addresses: a senior engineer can have a coding agent ship almost any feature faster than they can learn the underlying concept. Books generated by this skill exist because outsourcing the work is fine, but outsourcing the *understanding* erodes the substrate (framing + drift detection) that makes the engineer a useful driver of the agent in the first place. Slow learning is no longer just cognitively justified — in 2026 it's *economically rational*: building got cheap, so understanding is the line item the engineer can afford to spend on now.

This skill does not teach. It generates the artifacts that make teaching possible. The actual sessions run via the `teaching` skill, driven by the chapters this skill produces.

## When you're invoked

The user wants a learn-by-LLM book scaffolded for a target language, anchored against a real repo. They've consented to a process that takes 30–60 minutes of upfront work and produces a months-long learning arc.

If the user wants a quick tutorial, single-language refresher, or a one-shot guide, hand the wheel back. This skill is for *long-arc projects*, not microcontent.

## Teaching voice generated by this skill

Bookgen does not run the live lessons, but it writes the materials that shape the live teacher. Those materials must produce a consistent teaching experience across models.

**Write in a conversational teacher voice.** The generated book, chapter scripts, AGENTS.md guidance, and vendored teaching instructions should sound like a patient senior engineer pairing with the learner, not a terse task runner. Use second person. Explain why each step matters. Add the connective tissue that helps the learner form a model: what to notice, what pain this solves, where the analogy breaks, and what prediction to make before running code.

**Prefer guided prose over bare checklists for teaching moments.** Checklists are fine for setup and verification. Conceptual sections should talk to the learner: short paragraphs, direct questions, and explicit pauses. A chapter should feel teachable by an LLM in a warm Claude-like cadence even if the executing model defaults to blunt, matter-of-fact output.

**Control verbosity by purpose, not by model default.** Be more talkative where understanding is being built; be concise for mechanical commands and file trees. Avoid both extremes: no command-only "do X" lessons, and no long generic lectures that don't improve prediction or transfer.

**Separate durable prose from live chat.** Book chapters can be long-form because solo readers need enough context to work without an agent. Live LLM teaching must still be bite-sized: reveal one predict-pause, one concept slice, or one exercise step at a time, then wait. Do not generate `AGENTS.md`, chapter notes, or teacher instructions that tell the live agent to dump the whole lesson plan, all reflection questions, and all exercises in one message.

**Make progressive reveal explicit in generated materials.** Chapter scripts should contain clear pause markers, but the live-teacher instructions should say: ask the current question, wait, calibrate, then continue. The chapter is the curriculum; it is not a block of text to paste into chat.

When scaffolding `AGENTS.md` or copying teaching-mode guidance into a generated repo, include this voice and pacing requirement so future agents keep the same conversational teaching style.

## The seven-step workflow plus evidence preflight

### Step 1 — Confirm scope and intent

Before anything else, confirm:

1. **The target language.** Rust, Go, Swift, Zig, OCaml, Elixir, or other.
2. **The anchor repo.** GitHub URL or local path. Project the learner finds genuinely compelling — they'll spend months on this.
3. **The learner's prior background.** What languages they've shipped in production. Optional but high-value: what *pains* they've felt that the target language might solve. (Used to populate the pain-anchor table — rule 7 of the teaching skill.)
4. **The motivation.** Why this language, why this repo, why now. (Used to populate the `00c-why-i-built-this.md` chapter — the personal backstory.)

Surface these by asking. Don't fabricate.

### Step 2 — Analyse the anchor repo

Analyse current remote state: for a local checkout, `git fetch origin` and read `origin/<default>` (for example with a fresh clone or a worktree from it) rather than a possibly stale local branch, so chapters and anchor SHAs match what learners will clone.

Read enough of the repo to understand:

- **Architecture.** Is it a single binary? CLI tool? Library? Distributed system? Web app?
- **Scale.** Lines of code, file count, top-level module count. (Use `wc -l`, `find`, etc.)
- **Phase-able subdivisions.** Does the repo have natural milestones in its commit history (large feature commits)? RFCs in `docs/`? A CHANGELOG? A `ROADMAP.md`? Numbered phases? Use these to slice the learning arc.
- **Key concepts demonstrated.** Skim README, top-level docs, the most-changed source files. What does this repo teach if you read its code?
- **Prerequisite knowledge it assumes.** What does someone need to know *before* they can productively work through this codebase?
- **Languages used.** Often more than one (e.g., Rust + bash, Swift + Objective-C). The target language should be the majority.

**Two-phase, deterministic first (ported from Understand-Anything).** Get the structure from a script, not from eyeballing files. Run the bundled `scripts/sequence.py` against the anchor repo to produce a deterministic facts pass — a dependency graph, per-file fan-in/fan-out, the detected entry point, and key definitions — written to `docs/teaching/dep-skeleton.json` (plus a readable `suggested-order.md`). Reason over that JSON; **do not re-extract structure by hand.** Trust the script for *what depends on what*; spend your judgment on *what it means and how to teach it*. For large tour-mode repos (10K+ LOC), run `scripts/compute_batches.py` first and analyse in batches (disk-as-context-bus) rather than one linear read.

Save this analysis as input to step 3. Don't dump it on the user yet — it's working memory.

### Step 2.5 — Build the source map

Before turning the repo into curriculum, map the external knowledge the book depends on. This is lightweight for implementation-heavy books and deeper for research-shaped topics.

Create `<output-repo>/docs/teaching/source-map.md` (or `docs/research/<subject>/<topic>-review.md` when the project already has a research directory) with:

- **Canonical sources.** Official docs, specs, source code, RFCs, standards, or primary papers.
- **Consensus.** Claims the book can teach directly because they are stable and source-backed.
- **Tensions.** Real trade-offs or active disagreements. Branches are not tensions; identify the deeper question or say the debate dissolves.
- **Common misunderstandings.** False models learners bring from other languages, slogans, outdated docs, or terminology drift.
- **Pitfalls.** Runtime, tooling, platform, or ecosystem behaviours that surprise practitioners.
- **Gaps.** Thin evidence, version-specific caveats, or concepts deferred by the one-concept cap.
- **Curriculum tree.** Root → branches → real tensions → leaves → pitfalls. Branches are accepted subtopics; tensions are contested trade-offs or active disagreements under those branches.
- **Probe bank.** Diagnostic questions for each major misunderstanding or pitfall. A source map that says "people misunderstand X" should also say how a teacher can test whether the learner has that misunderstanding.
- **Sources kept and dropped.** Record why kept sources matter and why dropped sources were rejected, so future agents do not reintroduce weak material.

Use evidence depth appropriate to the topic:

| Level | Use when | Sources |
|---|---|---|
| 0 | Pure local code walkthrough | Anchor repo code only |
| 1 | Language/runtime/API behaviour | Official docs, specs, source code |
| 2 | Ecosystem practice or architecture | Docs plus expert commentary and postmortems |
| 3 | Research-shaped claims | Papers, surveys, citations, competing empirical evidence |

The source map is curriculum input, not a bibliography graveyard. Each planned session should inherit any relevant consensus/tension/pitfall/gap notes, plus the diagnostic probes that will surface misunderstandings before the chapter explains them.

### Step 3 — Pick a teaching mode and recommend it

Three modes the book can take:

| Mode | When to pick | Chapter shape |
|---|---|---|
| **Reproduce** | Repo is small (under ~10K LOC) and the learner has time to rebuild it from zero | Each chapter rebuilds one slice of the original. The original is reference, not gospel. |
| **Tour** | Repo is large (10K+ LOC) or the learner doesn't want to clone | Each chapter explores one major subsystem of the existing code, with predict-pauses about *what each function probably does* before reading it. |
| **Extend** | Repo is medium and feature-extension-friendly | Each chapter adds one new feature or subsystem that the original doesn't yet have. Good for fork-and-evolve learners. |

Pick a recommendation based on the analysis from step 2, *tell the user the recommendation with one-line reasoning*, and ask if they want to override.

### Step 4 — Generate the session plan

Convert the repo's natural structure into a session-by-session plan. **Cap at one new concept per session** (rule 3 of teaching skill). Let the number of sessions follow from the concepts; a 6-month project has typically run 25–50, a few more if the repo is dense.

Write this plan to `<output-repo>/docs/teaching/sessions.md`. Each row: session ID, concept, what we do that session.

**Start from the dependency-derived order.** `scripts/sequence.py` (step 2) wrote `docs/teaching/suggested-order.md` — a BFS-from-entry-point ordering (overview → core types → features → infrastructure). Use it as the *starting* sequence, then **override on pedagogical grounds**: the graph knows what depends on what; it does not know the one-concept cap (rule 3), defer-load (rule 8), or pain anchors (rule 7). Re-shape freely, but don't invent a structure the dependency graph flatly contradicts without a reason.

For each session, identify:
- The *one new concept* it introduces
- The artifact it ships (rule 13)
- The pain anchor (if any) — what pain in a prior language it solves
- The evidence posture (rule 20): consensus, real tension, pitfall, misunderstanding, and/or gap
- The Socratic pressure plan (rule 21): likely fuzzy terms, diagnostic probes, and what counts as Confused/Aware/Confident
- Sources from the source map that materially shape the session

If a session has more than one new concept, split it. If a session has no demonstrable artifact, name it as ceremony explicitly.

**Self-check invariant (prerequisite integrity).** Every concept a chapter lists in `requires:` must be `teaches:` by an earlier chapter (or an earlier book in the chain). After writing the plan, this must reconcile — `scripts/chain_index.py` validates it and `--strict` fails on an unresolved `requires:`. Treat an unresolved prerequisite as a planning bug to fix now, not a runtime surprise for the learner.

### Step 5 — Scaffold the book skeleton

Create the directory tree and chapter stubs:

```
<output-repo>/
├── AGENTS.md                          # teaching-mode declaration, points at vendored skill
├── README.md                          # what this book is, who it's for
├── .skills/
│   ├── teaching/                      # snapshot of the installed teaching skill
│   ├── humanizer/                     # optional snapshot, if supplied
│   └── VERSION                        # records the snapshot date and source skill versions
├── docs/
│   ├── book/
│   │   ├── README.md                  # TOC + how to read this book
│   │   ├── 00-introduction.md         # how learning works (predict, surface model, compiler-as-teacher)
│   │   ├── 00b-what-is-<X>.md         # required technical context
│   │   ├── 00c-why-i-built-this.md    # optional personal backstory
│   │   ├── 01-<title>.md              # first chapter (FILL with content as proof of concept)
│   │   ├── 02-<title>.md              # second chapter (stub)
│   │   ├── ... (one per session, all stubs except chapter 01)
│   │   └── NN-<final>.md
│   └── teaching/
│       ├── sessions.md                # session plan (from step 4)
│       ├── source-map.md              # evidence preflight: curriculum tree, probes, consensus, tensions, pitfalls, gaps, sources kept/dropped
│       ├── notes/                     # teacher's-eye notes per chapter — empty stubs
│       │   ├── 01-<title>.md
│       │   └── ...
│       ├── <lang>-anchor-table.md     # populated from references/anchor-tables/<lang>.md + learner's pain history
│       └── build-philosophy.md        # mode-specific learning contract
└── (optional) CONTRIBUTING.md         # if the project has setup steps the reader needs
```

**Vendoring (step 5 detail):**

- Run `scripts/scaffold.sh` with the sibling `teaching` skill installed, or pass `--teaching-skill-dir <path>`.
- Pass `--humanizer-skill-dir <path>` only when you want to vendor an optional writing skill.
- Write a `<output-repo>/.skills/VERSION` file recording the snapshot date and source skill versions.

The vendored teaching skill makes a fork of the book repo usable without the original author's skill setup.

**Sequencing + drift infrastructure (step 5 detail):** the scaffold leaves `docs/teaching/suggested-order.md` + `dep-skeleton.json` in place (from `sequence.py`), and once the seed chapters are verified against the current anchor, capture a structural-fingerprint baseline with `scripts/drift.py --book-repo <repo> --rebaseline` (writes `docs/teaching/.fingerprints.json`) so future drift runs can name exactly which chapters to re-verify.

### Step 6 — Write the seed chapters

Three chapters get *full content* up front; the rest are stubs:

1. **`docs/book/00-introduction.md`** — how learning works in this book. Explain that chapters are durable reading artifacts, while live sessions proceed one bite at a time: current idea, prediction, answer, next idea. Write for this learner and project.

2. **`docs/book/00b-what-is-<X>.md`** — the technical context everyone needs. Explain the domain, the architecture below the project, where the project sits, and the central question if one applies. Required reading.

3. **`docs/book/00c-why-i-built-this.md`** — the learner's reason for choosing this project, populated from their actual answers in step 1. Optional reading; omit it if they do not want to share a personal backstory.

4. **`docs/book/01-<title>.md`** — full first chapter, written using the `teaching` skill's chapter-template. This is the proof-of-concept the learner will see when they decide whether the book is for them.

**Write each seed chapter in passes, not one shot (Re3 / LongWriter).** Give each section an intent and a rough length budget; expand section by section. Then run two *separate* editorial passes: a coherence pass (does it follow the outline and reuse the prior chapters' terms?) and a factual pass (does every claim and code block hold up — see "Verify before publishing"?). Don't fuse them.

All other chapters get **stubs** with frontmatter, an outline and related reading.

### Step 7 — Companion artifacts

- **`AGENTS.md`** at the project root — declares teaching mode, points at the vendored teaching skill, includes the learner profile and the per-language pain anchor table. It must also state the live-session pacing contract: do not dump the whole lesson; teach one concept slice, ask/wait, then continue.
- **`docs/teaching/<lang>-anchor-table.md`** — populated from the appropriate `references/anchor-tables/<lang>.md` plus the learner's specific prior-language pains from step 1.
- **`docs/teaching/source-map.md`** — source-backed map from step 2.5. Include the curriculum tree, probe bank, consensus, real tensions, common misunderstandings, pitfalls, gaps, sources kept, and sources dropped.
- **`docs/teaching/build-philosophy.md`** — use the mode-specific template in this skill.
- **`docs/teaching/dep-skeleton.json` + `suggested-order.md`** — dependency graph and BFS-derived chapter order from `scripts/sequence.py`. The session plan is written over `suggested-order.md`.
- **`docs/teaching/.fingerprints.json`** — structural baseline for drift detection; create with `scripts/drift.py --book-repo <repo> --rebaseline` once the seed chapters are verified against the current anchor.
- **Repository handoff.** Initialize a repository when the output path is new. Commit only when the user or repository policy authorizes it; publishing remains a separate decision.

## Tools and references

### Scripts (bash + python helpers)

All scripts live under `scripts/` and are designed to be run repeatedly. None of them touch chapter content — chapters are the learner's work; scripts only manage the infrastructure around them.

- **`scripts/scaffold.sh`** — initial scaffold. Creates the directory tree, vendors the teaching skill and an optional humanizer skill, installs the anchor table and build philosophy for the chosen mode, writes `.skills/VERSION`, and optionally makes the first commit. Re-running only rewrites VERSION when mode, language or anchor differ.

- **`scripts/update.sh`** — refresh an existing book's infrastructure to the current bookgen world. Re-vendors the skills, refreshes the anchor table and build-philosophy, regenerates the chain index, runs drift detection, and reports what changed in the anchor codebase since the last update. Reads `.skills/VERSION` for state. Use this when you've improved bookgen and want existing books to benefit. Pass `--bootstrap-version` if the book predates `scaffold.sh` (no VERSION file) — it'll infer language and anchor from existing state and write a fresh VERSION.

- **`scripts/sequence.py`** — dependency-ordered chapter sequencer (port #1). Parses the anchor repo's imports/exports/calls (tree-sitter when available, regex fallback otherwise), detects the entry point, BFS-orders the files by depth, and writes `docs/teaching/dep-skeleton.json` + `suggested-order.md`. The deterministic skeleton the session plan (step 4) is written over. Two-phase by design: the script does the graph math, the agent reasons over the JSON.

- **`scripts/compute_batches.py`** — import-aware batching for large tour-mode repos (port #5). Splits the repo into cohesive ~25-file batches with a cross-batch `neighbor_map`, writes `docs/teaching/batch-plan.json`, and sets up `docs/teaching/intermediate/` for disk-as-context-bus fan-out. Use only when one linear read of the anchor is wasteful.

- **`scripts/lib/treesit.py`** — shared structural parser used by `sequence.py` and `drift.py`. One place to turn a file into `{imports, exports, defs, calls}` and a stable structural fingerprint. Optional `tree-sitter` + `tree-sitter-language-pack` accelerate it (see `scripts/requirements.txt`); without them it falls back to regex so nothing hard-fails.

- **`scripts/chain_index.py`** — generate the cross-book concept index at `<book-repo>/docs/chain/`. Walks chapter frontmatter for `teaches:` / `requires:` tags, reads `book-chain.toml` to find sibling books, and emits an index of which book teaches which concept and which depends on which. Also emits `concept-dag.json` — a machine-readable prerequisite graph (nodes, edges, unresolved) consumed by the teaching skill's rule 23 (recursive prerequisite descent). `--strict` exits non-zero on an unresolved `requires:`, so it doubles as the prerequisite-integrity gate from step 4. Run automatically by `update.sh`; can also be invoked directly.

- **`scripts/drift.py`** — detect drift between book chapters and the anchor codebase. Two layers: the original regex layer (moved paths, renamed symbols, stale SHAs) plus a **structural-fingerprint** layer (port #3). With a baseline (`--rebaseline` writes `docs/teaching/.fingerprints.json`), it classifies each changed file as *structural* (defs/exports/imports changed) versus *cosmetic* (size moved, structure identical) and names **which chapters to re-verify**. Tree-sitter gives accurate structure; regex fallback keeps it working without the dependency. Writes a numbered drift report to `<book-repo>/docs/issues/NNNN-drift-<date>.md`. Surfaces drift only — does not auto-fix.

- **`scripts/source_audit.py`** — future helper for source-map maintenance. Checks links, doc versions, and stale source claims against chapter frontmatter. If not scaffolded yet, create `docs/issues/NNNN-source-audit-needed.md` instead of pretending the audit exists.

- **`scripts/notes_meta.py`** — aggregate patterns across teaching-notes (`docs/teaching/notes/*.md`). Surfaces recurring wrong predictions, sticky concepts, refinement ideas, and artifact-landing observations across chapters. Useful before a session to see what cross-cutting issues have come up before.

- **`scripts/export_mdbook.sh`** — export the book as a static mdBook site. Generates `book.toml` and `src/SUMMARY.md`, copies all chapters + chain concepts in. Run after a session if you want to publish a snapshot.

### References (templates and tables)

- **`references/workflow.md`** — extended walkthrough of the seven steps, with worked examples.
- **`references/mode-selection.md`** — heuristics for picking reproduce / tour / extend, plus which templates each mode pulls from.
- **`references/anchor-tables/<lang>.md`** — pre-baked starter pain-anchor tables for Rust, Go, Swift, **SwiftUI** (Swift + iOS-specific patterns), Zig, OCaml, Elixir. Extend in-session with the learner's specific prior-language pains.
- **`references/templates/reproduce/`** — chapter / intro / what-is / why / README / AGENTS templates for **reproduce-mode** books (build from zero, runnable artifact per chapter).
- **`references/templates/tour/`** — chapter / chapter-01 / build-philosophy / README templates for **tour-mode** books (read existing code, paragraph-of-understanding artifact per chapter). Tour-mode chapter 01 has two sub-variants (own-code vs someone-else's-code).
- **`references/templates/chain/`** — `book-chain.toml` template (with TOML-ordering caveat baked in) and `concept-tags-spec.md` documenting the `teaches:` / `requires:` frontmatter contract.

## Voice

Write human-facing prose for the learner: settle the reader, the outcome, and the one takeaway of each chapter; put a mechanism or runnable example beside every claim. If `clarity` or `humanizer` skills are installed, use them during composition. The book must work without either one.

Specifically:
- Match punctuation and register to the learner's own writing sample when available.
- Avoid "delve, leverage, garner, pivotal, tapestry, intricate, showcase, foster"
- Avoid promotional language (vibrant, robust, comprehensive, powerful)
- Use second person ("you") for instructions; first person ("I") for backstory
- Vary sentence length aggressively
- No sycophantic asides ("Great question!"), no generic positive conclusions

## Verify before publishing

Any code, command, or expected-output block that lands in a chapter (or a milestone task file, or a README quickstart this skill scaffolds) must have been **run end-to-end on the target system first**, with the actual captured output pasted in verbatim.

**Treat verification as a loop, not a single check (Self-Debug / LEDEX).** For every runnable block: run it → on failure, feed the error back and repair → re-run → only then paste the captured output verbatim. Don't ship a block that hasn't gone green on the target system. Execution-feedback self-repair is a measurable accuracy lift in code generation; make it an explicit pipeline stage, not a hope.

This is rule 16 of the `teaching` skill. The skill enforces it for live-taught chapters; bookgen enforces it for *generated* chapters too. Reasons:

- Lessons that don't work erode learner trust and burn session time chasing accidents instead of concepts.
- Specs and docs drift; a port-format claim that was true in version 1.9 may be wrong in 1.10. The only source of truth is the system in front of the learner.
- Generated stubs are exempt (they're stubs by definition); but the *seed chapters* this skill produces (`docs/book/01-...md`, the "what is X" / "why I built this" chapters with embedded examples) are not stubs — verify their commands.

If verification reveals environment-specific behaviour (library version drift, OS-specific output format, tool version skew), capture it as `<output-repo>/docs/issues/NNNN-<slug>.md` *before* the chapter ships. The chapter then gets to anchor against verified-and-known reality. Also update `docs/teaching/source-map.md` if the discovery changes the chapter's evidence posture.

If a failure IS the lesson (a deliberate compiler-error walkthrough), label it inline so a future reader can't mistake it for accidental brokenness.

When fixing a published chapter that turned out broken: fix the downstream files that inherited the broken assumption too — milestone task files, sibling chapters, READMEs that copy-pasted the same code. Broken assumptions propagate; fixes should propagate.

## Smoke tests as deferred-load infrastructure

This is rule 17 of the `teaching` skill. Generated books include teacher-written smoke tests for each *filled* chapter (stubs are exempt) under the same deferred-load framing as `#[tokio::main]` and friends.

Principles lifted from the project's `tdd` skill:

- **Test the chapter's outcome promise, not the implementation.** Apply the Implementation Swap Test: could the learner rewrite the example from scratch — different control flow, different decomposition, different idioms — and have the test still pass? If yes, the test verifies behaviour. If no, it constrains learner creativity. Constraining creativity is the opposite of what teaching-time tests should do.
- **Expected values come from the chapter's promise, never from reading the implementation.** A chapter that opens with "by the end you'll see X" provides the assertion target.
- **One test per chapter, not exhaustive coverage.** Smoke-style only — the chapter's central artifact-level invariant. Edge cases wait for the dedicated TDD session, when the book retroactively explains testing as a concept.
- **Sequence: tests AFTER the teach-back, not before.** Tests verify behaviour; teach-back verifies understanding. Don't conflate.
- **Tests live where they don't intrude on the learner's reading flow.** Inline `#[cfg(test)] mod tests` (or whatever the language equivalent is) at the bottom of the example file is fine — invisible to a learner reading top-to-bottom for the lesson. Avoid putting tests in the chapter narrative; mention them in a footnote or "see also" only.
- **No test-driven introduction of new concepts to the learner.** If a smoke test would require the learner to see a generic bound, a trait import, or any other concept they don't have yet — refactor the test, not the example. Use loopback servers, in-memory pipes, fixture data, or subprocess invocation as needed to keep the learner-visible surface unchanged.

When generating a book, scaffold a placeholder smoke-test scaffold for each session that's been filled, so the learner-facing example file already contains an empty `#[cfg(test)]` block (or equivalent) ready for the teacher to fill after the first live run. The dedicated TDD session this generates explains how the existing tests work and transitions ownership to the learner.

## Chapter tags and releases

This follows rule 18 of the `teaching` skill. Add chapter-tag infrastructure when the user wants the book published with reproducible start states:

1. **Tag naming**: `chapter-NN` is the **start state** of chapter NN. Checkout the tag to begin the chapter. Tags are *not* "end of chapter" markers — they're "begin chapter NN here." So when chapter NN-1's session ships, tag the resulting commit as `chapter-NN`.

2. **Release workflow**: when the user wants to publish chapters, scaffold `.github/workflows/release.yml` (or platform equivalent) that fires on `chapter-*` tag pushes and creates the corresponding GitHub Release. Generate release notes from chapter frontmatter (`title`, `artifact`, `session_id`).

3. **Corrections**: keep published tags stable. Document a later correction and publish a new version or reference through the project's release process.

4. **Spoiler protection**: the chapter NN's *artifact code* (the example file the learner is about to write) should NOT be present at chapter-NN's tagged commit. The chapter file (lesson narrative) IS present so the learner can follow along. To enforce: hold the artifact file back to the next commit when the chapter ships, then the next session's tag includes it.

5. **CONTRIBUTING.md section**: when a release workflow is used, explain the chapter tag and release convention to readers cloning the repo.

The tag-per-chapter affordance is what makes the "fork and read at any chapter" property of learn-by-LLM books work. Without it, the book is linear-only — a learner has to walk every chapter or manually rewind. With it, anyone can `git checkout chapter-NN` and have the codebase in exactly the right shape to begin chapter NN.

## What this skill does NOT do

- It does not teach. After scaffolding, hand off to the `teaching` skill for live sessions.
- It does not lock you to the source repo's design. Chapters can deviate; repo is reference, not gospel.
- It does not auto-fill all chapters. Stubs get filled session-by-session as the learner walks the arc.
- It does not pick the language for you. The learner brings the target language.
- It does not skip verification. See "Verify before publishing" above. Generated chapter stubs that contain runnable code or expected output must have that code/output verified before the chapter is considered ready to teach from.
